# 学生智能助手需求梳理

版本：v0.1  
模块负责人：第五部分 - 学生智能助手  
依据：《客户需求表.xlsx》与 `db_init.sql`

## 1. 模块定位

学生智能助手面向在读学生，提供一个统一的对话式服务入口。它不是单纯的聊天机器人，而是由 AI 理解学生诉求、后端执行可信业务规则、企业端人员完成审批和跟进的学生服务模块。

覆盖七类场景：

1. 行政服务：请假申请、考务相关申请和申请结果查询。
2. 心理关怀与预警：情绪倾诉、风险识别、人工跟进。
3. 售后反馈：投诉、建议、咨询工单提交及处理进度查询。
4. 学业考务：成绩、考试、论文和其他关键 DDL 查询与提醒。
5. 申请进度追踪：院校申请、材料、录取和签证等阶段查询。
6. 海外生活支持：医疗、交通、紧急求助和日常生活问答。
7. 增值转化：识别升学或背景提升意向，推荐适合的项目。

## 2. 角色与责任边界

| 角色 | 可执行操作 |
|---|---|
| 学生 | 发起请假和反馈、查询成绩/DDL/申请进度、进行情绪倾诉、查询海外生活信息、查看本人业务状态、提交满意度评价 |
| 班主任/老师 | 查看待审批请假、接收高风险心理预警、填写心理跟进记录 |
| 顾问/售后员工 | 更新申请进度、处理投诉工单、填写解决方案 |
| 企业智能助手模块 | 提供员工侧请假审批、投诉处理、成绩录入和进度维护能力 |
| 智能报告模块 | 只读消费心理记录、心理预警和投诉工单，生成周报 |

学生助手负责学生侧的创建、查询、展示和 AI 编排；企业智能助手负责员工侧的审批、处理和维护。两端通过公共待办与通知能力协同，不重复实现同一业务动作。

## 3. 数据表范围

### 3.1 学生助手主业务表

| 功能 | 表名 | 使用说明 |
|---|---|---|
| 学生身份和归属 | `student_info` | 保存学号、学校、专业、留学国家、班主任等扩展信息 |
| 成绩查询 | `student_score` | 企业端录入，学生端仅查询本人数据 |
| 请假/考务申请 | `student_admin_service` | 保存请假类型、时间、事由、附件和审批结果 |
| 心理画像 | `student_psych_profile` | 保存最新情绪、分值、风险等级和周摘要 |
| 心理历史 | `student_psych_record` | 保存按日沉淀的情绪标签、摘要和触发关键词 |
| 心理预警 | `student_psych_alert` | 保存高风险触发原因、跟进老师、处理状态与记录 |
| 投诉反馈 | `student_feedback_ticket` | 保存工单摘要、详情、类别、优先级、处理状态与满意度 |
| 申请进度 | `application_progress` | 保存目标院校、阶段、截止日期、下一步和负责顾问 |
| 学业关键节点 | `academic_deadline` | 保存论文、考试、申请、签证等 DDL 及提醒配置 |
| 海外生活知识 | `overseas_life_knowledge` | 保存按国家和类别维护的海外生活知识 |

### 3.2 公共与跨模块表

| 用途 | 表名 | 责任边界 |
|---|---|---|
| 用户、班主任、顾问身份 | `sys_user`、`sys_role` | 公共系统能力 |
| 学生助手的意图与提示词 | `intent_config` | 学生场景已有七类意图种子数据 |
| 审批和跟进待办 | `todo_item` | 请假使用 `leave_approval`，投诉使用 `complaint_follow`，心理预警暂用 `custom` |
| 业务通知 | `notification_log` | 请假结果、工单状态、DDL 提醒等通知记录 |
| 对话历史 | `chat_session`、`chat_message` | 复用统一会话表；根据 `user_id` 和 `intent` 区分学生会话 |
| 升学项目推荐 | `course_project` | 由客服/课程模块维护，学生助手只读推荐 |

### 3.3 数据主键约定

所有学生业务表中的 `student_id` 统一按 `sys_user.id` 使用；学生详情通过 `student_info.user_id` 关联。`student_info.id` 仅作为学生扩展表自身主键，不应与业务表中的 `student_id` 混用。

## 4. 七类功能需求

### 4.1 行政服务：请假申请

学生可以通过对话或表单提交病假、事假、紧急请假，填写开始时间、结束时间、事由和可选附件。AI 可从自然语言中提取字段；字段缺失时必须追问，提交前展示确认信息。

提交后写入 `student_admin_service`，初始状态为 `pending`；同时为 `student_info.class_teacher_id` 创建 `todo_item`，并写入通知记录。班主任在企业智能助手审批后，学生端可查询审批意见和结果。

状态流转：

```text
pending -> approved
pending -> rejected
pending -> cancelled
```

### 4.2 心理关怀与预警

学生可进行日常情绪倾诉。AI 使用温和、支持性的语气回复，并输出结构化的情绪标签、情绪分值、风险等级和触发关键词。

- 低风险：写入心理记录，更新心理画像。
- 中风险：写入心理记录和画像，后续对话持续观察。
- 高风险：除更新记录和画像外，创建 `student_psych_alert`，指定老师跟进，并创建待办和通知。

心理模块的 AI 仅用于关怀和风险分流，不做医学或心理诊断。预警记录优先保存关键词或摘要，避免默认扩散学生完整原话；高风险回复需要提示学生立即联系可信任的人、学校相关人员或当地紧急支持渠道。

预警状态流转：

```text
pending -> following -> resolved
pending -> dismissed
following -> dismissed
```

### 4.3 售后反馈：投诉、建议与咨询

学生可以提交长文本投诉、建议或咨询。AI 对长文本生成工单标题、内容摘要、类别和优先级，学生确认后创建 `student_feedback_ticket`。

企业端负责指派处理人、更新状态和填写解决方案；学生端查看处理进度、解决方案，并在结案后提交 1 至 5 星满意度。

状态流转：

```text
pending -> processing -> resolved -> closed
```

### 4.4 学业考务查询

学生查询本人课程成绩、考试日期、论文 DDL 及其他关键节点。数据读取 `student_score` 和 `academic_deadline`，并按截止时间排序展示。

`academic_deadline.student_id` 为 `NULL` 时表示通用节点；学生查询时需同时返回通用节点和本人的专属节点。提醒由 `reminder_enabled`、`reminder_days` 和 `notification_log` 支持。

### 4.5 申请进度追踪

学生查询各目标院校的申请状态。返回内容包括目标院校、目标专业、当前阶段、进度说明、关键截止日期、下一步操作和负责顾问。

申请阶段统一使用数据库定义：

```text
document_prep -> submitted -> under_review -> offer_received -> visa_processing -> enrolled
```

学生端只读；顾问在企业智能助手或管理端更新 `application_progress`。

### 4.6 海外生活支持

根据学生的 `abroad_country`，在 `overseas_life_knowledge` 中检索对应国家的医疗、交通、紧急求助和日常生活知识。回答必须基于检索结果；未检索到可靠资料时应明确说明知识库暂无相关信息，不编造政策或紧急联系方式。

### 4.7 增值转化

当学生表达硕博、学历提升、背景提升、语言提升等明确意向时，查询已上架的 `course_project`，结合学生的专业、留学国家和申请阶段生成推荐理由与咨询引导。

推荐应保持克制：心理高风险对话、投诉处理进行中或学生明确拒绝营销时，不触发增值推荐。

## 5. Dify 与 FastAPI 职责划分

### 5.1 Dify 职责

学生助手使用一个 `学生智能助手` Chatflow。入口通过问题分类器分流至七类意图：`leave_request`、`emotion_chat`、`feedback_submit`、`academic_query`、`progress_query`、`overseas_life`、`upselling`。

Dify 负责：

1. 识别意图和追问缺失信息。
2. 提取请假字段、情绪结构、工单摘要和推荐偏好等 JSON 结果。
3. 检索海外生活知识库并组织回答。
4. 生成投诉摘要、关怀回复和推荐话术。

### 5.2 FastAPI 职责

FastAPI 负责：

1. 基于登录态确定当前学生，不信任对话中自行提供的学号或用户 ID。
2. 校验字段、权限和状态流转后执行写库。
3. 查询本人业务数据，限制学生跨用户访问。
4. 创建待办、通知、预警和审计记录。
5. 向 Dify 提供受控 HTTP 工具或封装后的接口。

Dify 不直接连接数据库、不直接执行 SQL、不直接审批请假或修改工单状态。AI 的结构化结果必须经后端校验后才能写入业务表。

## 6. 跨模块协同

```text
学生助手提交请假/投诉/预警
        |
        v
student_admin_service / student_feedback_ticket / student_psych_alert
        |
        v
todo_item + notification_log
        |
        v
企业智能助手：审批、跟进、更新状态
        |
        v
notification_log
        |
        v
学生助手展示处理结果
```

| 协作模块 | 学生助手使用内容 | 对方应提供内容 |
|---|---|---|
| 企业智能助手 | 请假、投诉、成绩、申请进度的共享业务表 | 员工侧审批/处理/录入接口与状态更新 |
| 客服 Agent | `course_project` | 已上架课程或项目的可查询数据 |
| 智能报告 | 心理记录、预警、投诉工单 | 只读统计，不修改学生业务数据 |
| 系统公共模块 | 用户、角色、待办、通知、意图 | 统一身份与通知能力 |

## 7. 首期实现优先级与验收

首期不平均铺开七项功能，优先完成可演示的闭环。

1. 请假申请 -> 班主任待办 -> 企业端审批 -> 学生收到结果。
2. 投诉提交 -> AI 摘要/分类 -> 企业端跟进 -> 学生查看方案并评价。
3. 成绩、DDL 和申请进度查询。
4. 心理情绪记录与高风险预警。
5. 海外生活 RAG 与增值项目推荐。

首期验收场景：

| 场景 | 预期结果 |
|---|---|
| “我明天上午要请病假” | AI 提取时间和类型，缺失字段时追问；确认后生成 `pending` 请假单和班主任待办 |
| 班主任同意请假 | 请假单更新为 `approved`，学生产生一条结果通知 |
| 学生提交长篇签证投诉 | AI 输出摘要、分类和优先级，确认后生成工单 |
| “我的论文截止日期是什么时候” | 返回通用和个人 DDL，并按临近程度排序 |
| “我的英国申请到哪一步了” | 返回本人申请阶段、下一步和截止日期 |
| 学生出现高风险表达 | 生成心理记录与预警，分配老师跟进；不将完整原话默认广播 |
| “我想咨询硕博申请” | 查询上架项目，返回匹配推荐和理由 |

## 8. 当前限制与待对齐事项

1. 当前表结构未建立外键，后端必须验证学生、老师、顾问和业务记录之间的关联关系。
2. `todo_item.todo_type` 没有心理预警专用类型，首期使用 `custom`，并以 `related_type` 标记为心理预警。
3. `notification_log` 记录发送状态，不提供已读状态；学生端首期以通知列表和业务详情状态为准。
4. 需求中提出实时拉取教务系统 DDL 和 CRM 申请进度，但当前项目未提供外部系统接口。首期使用本库数据演示，后续在服务层预留教务和 CRM 适配器。
5. `chat_session` 为统一会话表，首期通过 `user_id` 和消息 `intent` 区分学生会话；如未来需要多场景严格隔离，再评估新增场景字段。
